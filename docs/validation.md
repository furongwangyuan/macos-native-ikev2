# 验证范围与已知限制

## 原工程证据与公开版证据

原部署曾使用 Apple Silicon Mac 与 iOS 系统 IKEv2 完成单设备的 IPv4/IPv6/DNS、公网蜂窝、手动重连和 Wi-Fi/蜂窝切换测试。之后仍持续修复并发、恢复与观察边界问题，所以历史成功不能证明任意后续版本和网络环境都已通过实机验收。

公开版的源码检查和离线回归只证明相应模型与代码路径。测试中模拟的内核/VICI 事件不是两台真实手机同时连接，也不是中国大陆线路测试。发布时的实际命令和结果记录于 [publication-checks.md](publication-checks.md)。

## 2026-10-26 外层 IPv6 数据验证

深圳的原生 macOS strongSwan/PF_KEY 客户端与马来西亚网关完成真实证书认证和 CHILD 建立，并通过 IPv6 外层承载内层 IPv4、IPv6 HTTPS。较早的一次独立测试中，两族小 HTTP 响应均成功。后续同 SA 对照只比较 HTTPS：普通 MTU1500 路由下两族 HTTPS 均在 TCP 连接后超时；仅把两个测试目标的客户端主机路由 MTU 降到 1280 后，两族 HTTPS 均返回 200，检测到马来西亚出口。测试结束后移除了临时主机路由及客户端内核状态。服务端没有因此加入全局 MSS 或物理接口 MTU 修改。

再一轮原生客户端测试确认实际流程从 UDP500 IKE_SA_INIT 转到 UDP4500 IKE_AUTH，并在 MTU1280 下完成两族 HTTPS。该轮隧道内 IPv4 DNS 查询成功，IPv6 DNS 尚未通过，不能宣称所有 DNS 路径已验收。

这证明该原生客户端与该条跨境 IPv6 路径的数据面可用，不能代替 iPhone 测试。外层 IPv6 入口此后已上线，Apple 系统原生 Mac 参考测试也已通过内层双栈 HTTPS；当前版本的真实 iPhone、Wi-Fi/蜂窝切换、多设备持续流量及长期、跨运营商表现仍待验收。iOS 配置设置 MTU1280；未测试地址变更热更新，前述连接测试本身不构成吞吐验收。原始地址、身份、凭据、抓包和安装收据没有随源码公开。

## 2026-10-26 双身份断开与重连

一次真实跨境测试使用深圳同一台 Mac 上的一个原生 strongSwan 进程，建立两个独立证书身份、独立虚拟地址和独立 IKE/CHILD 会话。两身份并发访问、仅断开 A 时保留 B、再重新连接 A 的过程中，发现 macOS 的合法三端点 NAT 状态输出被误判，导致共享服务恢复。

只修复该解析问题的版本随后完成相同测试：11/11 个 HTTP 检查成功，B 的 IKE/ESP 会话保持不变，服务端守护进程没有重启。这是两个真实身份上下文，不是两台 iPhone 并发验收。原始身份、地址和状态记录未公开。

本次源码还包含“未知状态读回只延期受影响设备”的后续修复。持续失败、重新连接和隔离恢复通过了离线回归。该版本的第一轮实机复测（I5）为 9/11：重新连接 A 后，两族请求都在原有 3 秒连接期限内失败；同时 B 的请求成功，会话不变，共享守护进程未重启。这两次失败保留，不能以服务仍在运行代替数据成功。

下一轮（I6）保留相同请求与超时，原 11/11 成功；随后额外等待 5 秒发起的四次请求也全部成功，两组结果分别统计。B 的 IKE/ESP 会话保持不变，服务端守护进程未重启。A 的首次重连请求仍需约 2.25 秒，而稍后请求约 0.25 秒。高频持久状态观察显示，旧 A 的清理已核验完成后，新 A 仍需等待准入；没有证据把主要等待归因于持续的未知状态清理延期。准入时延仍有波动，具体耗时继续诊断，未把本轮成功写成稳定性问题全部解决，也未进行实机未知格式故障注入。

## 2026-10-26 短时吞吐与 IPv4 入口对照

原生客户端经 IPv6 外层隧道下载 IPv4 HTTPS 载荷：单 TCP 连接连续下载 200 MB，阶段墙钟约 7.97 秒，有效载荷平均约 200.7 Mbps；两个 TCP 连接合计下载 200 MB，约 5.80 秒、合计约 275.9 Mbps。全部 20 次请求返回 HTTP200 且长度符合预期，两阶段使用同一 VPN 会话。这是一个客户端、两个短阶段的结果，不是两台设备或长期持续吞吐验收；该轮另一个 IPv6 HTTPS 小探针超时，未把它算作成功。

下载期间双流有更多 TCP 重复序号覆盖和两端 ESP 抓包差额；现有采集不能把差额等同物理链路丢包率。观察期间未见整体 CPU 打满，但不是逐核瓶颈排除证明，因此没有仅凭此结果继续修改 TCP 参数。

另一次既有公网 IPv4 入口对照中，UDP500 初始化往返成功，随后四轮 UDP4500 认证请求及对应回复均在网关侧观察到，但客户端没有收到认证回复，最终超时。问题范围仍是网关发送观察点到客户端接收观察点之间，未定位到具体运营商、设备或过滤机制。该次没有 CHILD 或业务数据成功，IPv6 路径成功也不能代替 IPv4 路径验收。

## 2026-10-26 服务调度与重连时延

实际准入计时发现，服务的 launchd `ProcessType=Background` 让本地审核和规则更新受到后台调度限制。同一脚本的两次默认调度读取与一次后台调度读取显示，后台阶段的关键读取中位耗时为两组默认值的约 5.65–6.28 倍。

随后保持同一临时计时工具、准入检查、轮询间隔和客户端流程，只将服务调度改为 `Standard`。I9/I10 两轮各 15/15 次 HTTPS 请求成功，B 在 A 断开和重连期间保持相同 IKE/ESP 会话。A 认证回复到准入状态持久化的同机观测间隔从约 **4.149 秒降到 0.496 秒**；重连后的首个 IPv4/IPv6 TCP 建连从 **2.091/2.083 秒降到 0.085/0.079 秒**。稳定双身份循环的中位耗时从约 **1.207 秒降到 0.274 秒**。

上述准入时间使用网关同一时钟的报文与状态文件时间，不混算两地时钟；状态持久化时间也不等于精确的首包放行时刻。这是有界的原生 Mac 客户端对照，不能代替实体 iPhone 切网或长期性能验收。I10 的 B 单独存续阶段，两族请求仍出现约 **1.08 秒**建连，作为独立问题继续分析，没有把调度修正表述为全部延迟已经消失。

去除临时计时工具、保留相同 `Standard` 设置的最终版本随后完成 I11：15/15 次 HTTPS 请求成功，A 的认证回复到准入持久化约 **0.685 秒**，重连首个 IPv4/IPv6 TCP 建连为 **0.084/0.077 秒**，对应整个小请求约 **0.262/0.246 秒**。B 的 IKE/ESP 会话仍保持不变，客户端清理回读通过。

I11 中 B 单独存续阶段的 IPv4/IPv6 建连为 **0.088/0.236 秒**，此前约一秒停顿没有复现；这不能证明偶发问题已经修复，仍保留调查。该轮网关 IPv6 IPsec 错误计数没有增加，成功处理计数增加入站 234、出站 171；这些是整机计数，不能当作单设备计数或此前从未出错的证明。公开源码保留 `Standard` 及对应的固定配置校验器，没有加入临时计时工具、原始观察记录或部署端资料。

## 2026-10-26 监控页面重复绘制

监控页面原先每秒先用旧快照完整绘制一次，状态请求完成后又绘制一次，包含近 24 小时的每 30 分钟用量图。现改为正常请求完成后绘制一次；请求仍未完成或暂停请求时，每秒继续更新保留数据的过期提示。状态接口仍每秒请求，历史接口仍每分钟刷新，没有改变采集、统计区间或 VPN 服务。

五项离线调度回归通过：三轮快速请求的绘制次数由六次降为三次；慢请求不重叠且继续更新过期提示；失败立即呈现；隐藏页面停止轮询；跨日继续读取两天历史。该回归运行实际刷新与定时逻辑，只替换网络和绘制调用，不是浏览器视觉或网络时延验收。此优化减少页面重复工作，不作为 VPN RTT 改善的证据。

## 2026-10-27 选择范围就绪与客户端断线边界

持续观察中，一次完整 VICI 读取因 CHILD 的 `local-ts` 未匹配预期双栈通配范围而抛错，进入共享服务恢复。没有保存该异常范围的原值，不能认定普通换钥会清空范围，也不能声称已复现当时的原始帧。

本次修正该错误处理类别：完整且已归属设备的 CHILD 中，结构有效、最多16项的 `local-ts` 差异只使整设备处于 pending/overlap。所有兄弟 CHILD、原始状态及代信息仍保留；其他字段、跨设备 SPI/reqid 归属和完整内核策略审计继续执行。恰好两项双栈通配范围才可就绪，没有放宽转发授权。合成回归覆盖坏设备旁的健康设备继续工作、异常兄弟不能被跳过、恢复须重新通过原有多帧核验，以及其他违规仍被拒绝；这些回归不等于故障原帧复现或长期实机验收。

随后一次计划服务重启中，Mac 的普通手动 IKEv2 配置确实启用了 `IncludeAllNetworks`，但客户端收到服务端 DELETE 后完整停止隧道，进入正式 disconnected 状态，再自动重新连接。一条普通 HTTPS 请求在与该断开窗口重叠的时间内成功使用本地公网出口。客户端之后自动重连，下一轮请求恢复通过隧道；采样脚本没有主动重启客户端。恢复成功不能消除直出反例，整数秒请求时间也不能证明准确暴露时长。该观察不定位 Tailscale 共存的因果关系，不外推 iPhone，也不证明持续 connecting/reasserting 阶段有同样行为。

Apple 将 [IncludeAllNetworks 路由约束](https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic)、On Demand 和 Always On 区分。普通手动配置的全流量选项不能当作本项目已验证的永久断线阻断保证；未来的 On Demand 调整也需独立验证。本次没有更改客户端配置，原始地址、设备身份和私有日志未公开。

## 尚不能作出的保证

- 没有通用空白 Mac 一键部署验收；原升级模板依赖部署绑定。
- 不保证所有 macOS/iOS 版本、SDK、路由器或运营商兼容。
- 没有完成中国大陆各运营商可达性、延迟和约 200 Mbps 的验收。
- 离线多设备回归不能代替真实多设备并发及长期负载测试。
- 普通个人 VPN 配置不能保证控制所有系统级流量、GPS 或蜂窝定位；Mac 的正式断开窗口已有直出反例，尚无零泄露保证。
- IPv6 当前依赖家庭宽带 IPv6 与 macOS NAT66；不等于每个客户端拥有运营商路由前缀。
- 自动重试有资源预算。持续共享资源故障仍可能需要管理员恢复，不能承诺任何错误下永不停止。

## 新部署最小验收

1. **宿主基线**：VPN 关闭时 Mac 的 IPv4、IPv6、DNS 正常，记录网络配置。
2. **单设备数据面**：蜂窝连接后 IPv4/IPv6 出口均属家庭宽带；DNS 请求路径符合配置。
3. **开关与断线保护**：分别检查主动关闭、服务端终止会话和连接中重试；Mac 正式断开窗口已有直出反例，其他设备仍须独立检查，恢复后验证业务。
4. **重连与换钥**：手动开关、CHILD/IKE 换钥、两个方向的 Wi-Fi/蜂窝切换；记录首个新请求/视频的恢复时间。
5. **两台真实设备并发**：独立身份和地址；一台换钥/断开/撤销时，另一台业务持续可用。
6. **宿主恢复与重启**：停止、异常退出、服务器重启之后，Mac 网络和 VPN 都能按设计恢复。
7. **实际性能**：用同一手机、位置、运营商和站点做直连/VPN 对照；分别记录上下行、RTT、丢包与持续运行时间。

失败时保留与对应设备/时间段有关的最小脱敏记录。不要把含真实 IP、设备身份、令牌或完整私有配置的日志提交到公开 issue。
