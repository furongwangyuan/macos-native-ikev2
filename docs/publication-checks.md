# 源码发布检查

本文件记录公开源码快照的检查，不能替代部署与手机端验收。

所有检查以普通用户运行，没有更改正在使用的 VPN、路由器、PF、launchd、PKI、DDNS 或在线监控站点。原生编译配方在本次发布中进行语法和输入清单检查；未重新编译整套 strongSwan，也未在新 Mac 上安装。

可在干净检出中重跑：

```sh
python3 scripts/check_source.py
python3 -I -B server/tools/build_reference.py --check
python3 -I -B tests/server/run.py
python3 -I -B tests/native/pf_syntax.py # macOS only; syntax checks, no rule loads
bash -n native/build-native.sh
python3 -I -B monitor/check.py
python3 -I -B ddns/check.py
python3 -I -B maintenance/check.py
node --test monitor/uploader/check-loop.mjs
cd web
npm ci
npm test
```

`check_source.py` 检查文本源码、Python 语法、JSON、相对文档链接和常见凭据格式。它不是能识别一切秘密的证明；发布前另做了部署标识、嵌入资源及第三方许可人工审阅。

`tests/server/run.py` 禁止真实 socket、Popen 和 os.system；其策略/会话测试使用合成状态。监控、DDNS 和维护测试用模拟 IO，不使用真实凭据或发送 DNS 更新。构建输出放在忽略的 `build/` 目录，未作为可安装发行二进制发布。

`tests/native/pf_syntax.py` 单独调用 macOS 自带的 PF 编译器；每次调用都固定带 `-n`，只解析测试规则，不加载规则、不更改 PF 或转发设置，也不要求管理员权限。非 macOS 平台会跳过这些测试。

## 2026-10-25 PF 编译一致性修正

当 IPv6 地址列表变长时，PF 默认优化器可能将规则展开结果合并成自动命名的表。语法检查和实际加载分别生成的表名可能不同，使严格回读比较将等效规则误判为异常，进而停止服务。修正只为本项目生成的 anchor 输入添加 `set ruleset-optimization none`，保留明确的规则目标；没有放宽回读比较，也没有修改全局 PF 配置。单设备与多设备的操作记录现在都对实际保存的编译输入计算哈希。既有固定 guard 文本保持不变，便于旧会话恢复。

新增五项隔离回归覆盖输入持久化、哈希和不匹配拒绝，以及三项真实编译器语法回归覆盖匿名表复现、明确目标保留和原 guard 语义。服务器隔离测试增至 25 项。编译器测试只证明编译行为；手机连接与长期运行仍需部署端验证。

## 2026-10-25 已知 PF 回读异常自动恢复

两种已知的激活规则回读错误，在协调器确认关闭保护且完整清理、内核回读通过后，进入自动重试。达到每 900 秒最多三次启动的限制时，等待最早一次启动记录过期后再尝试；不因这种已知且已完成清理的错误永久暂停。恢复过程意外中断后也重新核验状态，再继续等待。未确认的规则变化和清理失败不使用这个恢复分类。

新增 14 项隔离测试后，服务器测试共 39 项通过。维护工具新增六项已知原因判定检查，共 57 项检查及 28 组恢复测试通过。上述验证使用模拟状态，没有向运行中的服务注入故障。

## 2026-10-25 缩小故障影响和保留会话

本轮修正五个运行文件。单设备路由读取失败或精确超时只关闭该设备的地址；连接状态的已知暂时读取失败先保留 charon/IKE 会话，在关闭数据转发后重新完整审核，连续第三次失败再走完整恢复。已确认且清理成功的五类服务中断都可等待启动额度释放后继续，不再因三次启动额度用尽而永久暂停。另修正守护进程退出观察中的竞态，并让可选诊断输出失败不覆盖实际恢复结果。

新增 22 项生命周期/恢复回归、7 项设备路由隔离回归和 7 项同进程恢复回归；更新此前只允许 PF 异常等待额度的旧断言。服务器隔离测试合计 75 项通过。双设备测试明确检查设备 A 路由失败后 B 的转发保持、A 恢复后重新准入；连接读取测试覆盖第一、第二和发布后观察阶段、连续失败退回完整恢复、状态来源保留，以及真正控制器继续运行而不执行守护进程清理。

源码检查覆盖 371 个文件，运行源码闭包仍为 131 个文件。这些都是隔离验证，没有让真实客户端经历人为故障；真实多设备和持续运行仍需现场观测。

## 2026-10-25 恢复程序持续运行

未分类错误、启动失败、暂时不可读的配置或状态，以及清理失败，现在进入持续恢复循环。`ATTENTION` 表示等待重新检查，不再表示正常退出后永久停服。恢复成功后仍需读取当前配置、验证激活记录并完成新的启动前检查；清理结果未确认时不启动第二个守护进程，也不放行数据。每 900 秒最多三次实际启动的限制保持不变，额度用尽只等待，不退出。

清理返回失败或抛出异常时，保留当前 owner 和进程引用，直到完整清理与回读通过。启动入口的开机恢复失败使用新的 Native 实例重新取得锁，避免复用已绑定的写入器；服务循环意外抛错则保留同一个 Supervisor 和 owner。可选日志失败不影响这些恢复动作。手动停止会打断等待并释放锁，让停止入口继续完成恢复。

此前服务记录处于 `ATTENTION`，不再单独否决跨开机周期的恢复；配置、源文件、原始记录绑定和内核恢复证明仍必须全部通过。若原生 journal 缺失，只允许使用既有的完整只读检查确认 PF、IPsec、转发、端口和进程均处于关闭状态；不生成假的清理记录。持久状态损坏或仍有原生残留时继续等待重新检查，不把未知状态当成正常空状态。

`test_persistent_recovery.py` 覆盖恢复循环和持久状态故障；`test_entry_recovery.py` 覆盖入口重试、持锁 owner 的保留、手动停止、跨开机周期准入及 journal 缺失检查。验证均为隔离故障注入，不向正在使用的 VPN 注入错误。

本轮服务器隔离测试共 101 项通过；源码扫描 373 个文件未发现问题，运行源码闭包 131 个文件通过语法与清单检查。

## 2026-10-26 PF 状态格式与设备清理隔离

真实双身份断开/重连时，macOS 可把 NAT 状态打印为“原始端点 → 转换端点 → 对端”。旧解析器只接受一个箭头，会把另一台设备的正常状态当作异常，导致共享服务恢复。当前解析器接受精确的三端点同向双箭头格式，逐一检查所有端点，保留旧括号格式；混合方向、错误地址和端口仍拒绝。

设备已从活动表撤下后，若固定状态读取暂时失败、输出仍不认识或地址状态尚未消失，协调器接收明确的延期结果，只阻止该设备重新准入。每个后续循环重试一次，其他设备保持正常审核和转发；持续未知状态不会单独触发共享守护进程重启。真实删除失败、共享规则/表变化及所有权错误仍然单独报错，没有把未知输出当作清理成功。

新增 **8 项格式回归**及 **9 项延期隔离回归**，并把原残留状态测试更新为核对延期收据；服务器隔离测试共 **165/165** 通过。源码检查 **383 个文件**无问题，服务器参考闭包 **132 个文件**通过。参考包由原 `build_reference.py` 生成并逐文件回读哈希，仍标记 `deployable: false`。只同步三个运行模块及脱敏测试/文档，没有复制运行日志、身份、抓包或部署收据。解析修复版本的实机结果与延期版本的验证边界分别记录在 [validation.md](validation.md)。
